Unit I: Introduction to Operating Systems, Dual Mode & Linux

Q1. Define an Operating System. Explain its objectives, core functions, and dual role as a Resource Manager and Control Program. Differentiate between Batch, Multiprogramming, Time-Sharing, Network, Distributed, and Real-Time Operating Systems with examples. 7 Marks • SPPU QB U1-Q1/Q2/Q3
SPPU Marking Split: Definition & Objectives (1.5M) · Resource Manager/Control Program & Core Functions (2M) · OS Types Comparison Table (2.5M) · Examples & Summary (1M)

1. Definition & Core Principle

An Operating System (OS) is system software that acts as an intermediary between computer users (application programs) and computer hardware, providing an environment in which a user can execute programs conveniently and efficiently while safeguarding hardware resources.

2. Objectives, Dual Role & Core Functions

  • Three Primary Objectives: (a) Convenience (abstracts complex hardware registers/sectors into files and windows), (b) Efficiency (maximizes CPU, RAM, and I/O utilization), and (c) Ability to Evolve (modular kernel design allows adding drivers and features without disrupting user programs).
  • OS as a Resource Manager (Allocator): Acts as an unbiased referee managing CPU cycles, primary memory, disk space, and I/O devices among competing processes, resolving conflicts fairly to maximize throughput.
  • OS as a Control Program: Supervises user-program execution to prevent illegal memory access, infinite loops, and hardware corruption, enforcing security and privilege isolation.
  • Five Major Functions: (1) Process Management (creation, scheduling, synchronization), (2) Memory Management (allocation, paging, virtual memory), (3) File & Storage Management (directories, access control, disk scheduling), (4) I/O Device Management (buffering, caching, spooling, drivers), and (5) Protection & Security (authentication, permissions).

3. Comprehensive Comparison of Operating System Types

Batch OS Similar jobs are grouped into batches by an operator and run sequentially. High turnaround; zero direct user interaction during run. Low (CPU sits idle during slow I/O). Good for repetitive payroll/billing; hard to debug interactively. IBM OS/360, SCOPE
Multiprogramming OS Multiple jobs stay in RAM; when one waits for I/O, OS switches CPU to another job. Non-interactive; switches only on I/O wait or completion. High (keeps CPU busy whenever a job is ready). Eliminates I/O idle gaps; requires memory protection & job scheduling. Early UNIX, IBM OS/MFT

4. Key Takeaways

  • Multiprogramming maximizes CPU utilization using non-preemptive I/O switching, whereas Time-Sharing maximizes responsiveness using preemptive timer interrupts.
  • Hard RTOS is mandatory in automotive airbags and avionics; Soft RTOS suits multimedia streaming and telecom routers.
Q2. Explain Dual-Mode Operation in an Operating System (User Mode vs Kernel Mode). Why is mode switching necessary, and how does a System Call / Trap transition between modes? 6 Marks • SPPU QB U1-Q8
SPPU Marking Split: Definition & Mode Bit (1M) · Neat Labelled Dual-Mode SVG + Explanation (2.5M) · Step-by-Step Transition & Need (1.5M) · Privileged Instructions & Takeaways (1M)

1. Definition & Core Principle

Dual-Mode Operation is a hardware-enforced CPU protection mechanism using a dedicated mode bit inside the Processor Status Word (PSW): mode bit = 1 denotes User Mode (restricted execution for application code) and mode bit = 0 denotes Kernel / Supervisor Mode (unrestricted access to hardware and privileged instructions).

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam)
  • Step 1 (User Mode, bit = 1): The user process executes arithmetic and logic instructions inside its isolated virtual address space and invokes a C library wrapper such as read().
  • Step 2 (Trap / Software Interrupt): Executing the CPU syscall / int 0x80 trap instruction automatically saves the user Program Counter (PC) and switches the hardware mode bit from 1 to 0, jumping to the kernel interrupt vector.
  • Step 3 (Kernel Mode, bit = 0): The OS inspects the system-call number, validates user pointers, executes privileged disk/MMU instructions on behalf of the caller, and places results into the user buffer.
  • Step 4 & 5 (Return from Trap): The kernel executes iret / sysret, resetting the mode bit back to 1 and restoring the user PC so the application resumes safely.

3. Why Mode Switching is Necessary & Mode Comparison

Without dual-mode protection, a buggy or malicious user application could overwrite OS kernel memory, disable hardware interrupts (freezing the entire system), directly format disk sectors, or hijack another process's memory. Any attempt to execute a privileged instruction (e.g., HLT, I/O port writes, modifying page-table base registers, changing the mode bit) while mode bit = 1 triggers an immediate hardware illegal-instruction trap to the OS.

Access ScopeRestricted to the process's own virtual memory space.Full unrestricted access to all RAM, CPU registers, and I/O devices.
Privileged InstructionsBlocked by CPU hardware (causes protection fault/trap).Permitted (interrupt masking, timer setup, MMU, context switch).
Crash ImpactOnly the faulty application terminates (e.g., Segmentation Fault).Kernel panic / Blue Screen (crashes the entire computer system).
Typical Code RunningBrowsers, compilers, user C/Python programs, shells.OS kernel scheduler, device drivers, interrupt handlers, VFS.

4. Key Takeaways

  • Modern CPUs (x86 Protection Rings 0–3, ARM EL0–EL3) extend dual-mode into multi-ring and hypervisor modes for virtual machines.
  • A timer interrupt ensures the OS periodically regains Kernel Mode control even if a user program enters an infinite loop.
Q3. List and explain Operating System Services. Define a System Call, classify the 6 categories of System Calls with Linux/Windows examples, and describe how parameters are passed to the OS. 6 Marks • SPPU QB U1-Q5 & SB Patil U1-Q3/Q5/Q6
SPPU Marking Split: OS Services (1.5M) · System Call Definition & Parameter Passing (1.5M) · 6 Categories Table (2M) · C Program Example (1M)

1. Definition & Core Principle

A System Call is the programmatic interface through which a user-space process requests a privileged service from the OS kernel. In practice, applications invoke high-level API functions (POSIX/glibc on Linux or Win32 API on Windows) that internally trigger a hardware trap to execute the corresponding kernel system call.

2. Operating System Services (Two Groups)

A. User-Facing Services
  • User Interface (UI): CLI (Bash shell), GUI (Desktop), or Batch command scripts.
  • Program Execution: Loading binaries into RAM, initializing registers, and terminating cleanly.
  • I/O Operations: Abstracting disk/network/keyboard hardware via drivers.
  • File-System Manipulation: Creating, deleting, searching, and setting file permissions.
  • Communications: IPC via shared memory or message passing across processes/networks.
  • Error Detection: Catching CPU/memory parity errors, power faults, or illegal opcodes.
B. System-Efficiency Services
  • Resource Allocation: Distributing CPU cycles, RAM frames, and I/O bandwidth among concurrent users/jobs.
  • Accounting: Logging CPU time, disk blocks, and network usage for billing or performance profiling.
  • Protection & Security: Ensuring isolated process execution and authenticating users with passwords/tokens before granting external access.

  • Standard libraries (printf(), malloc()) are user-space wrappers; they only enter the kernel via system calls like write() or brk()/mmap() when needed.
Q4. Explain Operating System Structures: Monolithic, Layered, and Microkernel architectures with neat diagrams. Compare their design trade-offs, advantages, and disadvantages. 7 Marks • SPPU QB U1-Q4 & SB Patil U1-Q2/Q4
SPPU Marking Split: Introduction (1M) · 3-Architecture SVG + Explanation (2.5M) · Comparative Analysis Table (2.5M) · Hybrid Kernels & Takeaways (1M)

1. Definition & Core Principle

OS Structure (Kernel Architecture) defines how internal operating system components (CPU scheduler, memory manager, file system, device drivers, and IPC) are organized across User Space and Kernel Space to balance raw execution speed against modularity, security, and fault isolation.

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam)
  • Monolithic Kernel: Every OS service (VFS, scheduler, drivers, networking) shares one flat kernel address space and communicates via fast C function calls.
  • Layered Approach: Organizes the OS as a strict hierarchy from Layer 0 (Hardware) to Layer N (UI), where layer $k$ invokes only routines provided by layer $k-1$.
  • Microkernel: Strips the kernel down to bare essentials (IPC, basic scheduling, low-level address space). File systems and device drivers execute as isolated user-space servers exchanging messages via kernel IPC.

  • Linux remains structurally monolithic at runtime, yet achieves extensibility using Loadable Kernel Modules (LKMs) via insmod/modprobe.

Q6. Differentiate between Network Operating System (NOS) and Distributed Operating System (DOS). Also explain Spooling vs Buffering with suitable examples. 5 Marks • SPPU QB U1-Q7 & SB Patil U1-Q12

1. Definitions & Core Principle

A Network Operating System (NOS) provides networking protocols and server services over loosely coupled independent machines where users remain explicitly aware of multiple hosts. A Distributed Operating System (DOS) manages a collection of autonomous machines connected by a network so that they appear to the user as a single unified computer (single-system image).

2. Comparison: Network OS vs Distributed OS

3. Spooling vs Buffering

  • Spooling (Simultaneous Peripheral Operations On-Line): Uses secondary disk storage as a large intermediate queue between a fast CPU and a slow output device (like a shared printer). Multiple jobs spool documents onto disk simultaneously, allowing the CPU to continue executing other processes while the print daemon feeds jobs sequentially to the printer.
  • Buffering: Uses fast primary memory (RAM) to temporarily hold data while transferring between devices with mismatched speeds or block sizes (e.g., streaming video buffer or keyboard input buffer). Unlike spooling (disk-based, multi-job), buffering operates in RAM for a single active stream.

4. Key Takeaways

  • Think of DOS as a single logical OS spanning multiple CPUs, whereas NOS is multiple autonomous OSes collaborating over network shares.
  • Spooling overlaps I/O of one job with CPU computation of other jobs using disk queues.

Q1. Define a Process and distinguish between a Program and a Process. Explain the 5-State and 7-State (Suspended) Process Lifecycle with a neat state transition diagram. 7 Marks • SPPU QB U2-Q1 & SPPU Oct 2025 Q3a
SPPU Marking Split: Definition & Program vs Process (1.5M) · Neat 7-State Lifecycle SVG + Explanation (3M) · Detailed Transition Descriptions (2M) · Takeaways (0.5M)

1. Definition & Core Principle

A Process is an active program in execution. Unlike a passive executable file stored on disk, a process encompasses the program text (code), current activity (Program Counter and CPU registers), execution stack, dynamic heap, and initialized/uninitialized data sections.

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam)
  • Core 5 States: New (PCB created) → Ready (loaded in RAM awaiting CPU) → Running (executing on a CPU core) → Waiting/Blocked (paused for I/O or signal) → Terminated (finished; OS reclaims resources).
  • Key Transitions: Admit (Long-Term Scheduler), Dispatch (Short-Term Scheduler), Interrupt / Time-Quantum Expired (preemption back to Ready), I/O Wait (Running → Waiting), and I/O Complete (Waiting → Ready).
  • 7-State Swap Extension: Under RAM pressure, the Medium-Term Scheduler swaps blocked/ready processes to disk (Blocked-Suspended / Ready-Suspended). If the awaited I/O finishes while swapped out, it transitions from Blocked-Suspended → Ready-Suspended.

3. Program vs Process Comparison

BasisProgramProcess
NaturePassive static entity stored on disk (executable file).Active dynamic entity loaded in RAM during execution.
LifespanPermanent until explicitly deleted from storage.Temporary; exists only from creation to termination.
Resources NeededDisk storage space only.CPU time, RAM (stack/heap/data), open files, I/O devices, PCB.
MultiplicityOne program binary can spawn many independent processes.Each instance has a unique PID and separate memory state.

4. Key Takeaways

  • Only one process per CPU core can be in the Running state at any instant, while many can wait concurrently in Ready or Waiting queues.
Q2. What is a Process Control Block (PCB)? Explain its structure and fields with a neat diagram. Define Context Switching and analyze its overhead on system performance. 7 Marks • SPPU QB U2-Q2/Q7 & SPPU Oct 2025 Q4a
SPPU Marking Split: PCB Definition & Role (1.5M) · PCB + Context Switch SVG & Explanation (2.5M) · Detailed PCB Fields (2M) · Performance Impact (1M)

1. Definition & Core Principle

A Process Control Block (PCB) (also known as a Task Control Block, e.g., struct task_struct in Linux) is a kernel-maintained data structure serving as the repository of all metadata required to manage, pause, and resume a specific process. Context Switching is the mechanism of saving the CPU state of the outgoing process into its PCB and restoring the saved state of the incoming process from its PCB.

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam)
  • Left (PCB Fields): Every active process has its own PCB holding identity (PID), execution checkpoint (PC & CPU registers), scheduling priority, page-table pointers, and open file descriptors.
  • Right (Context Switch): When an interrupt or time-slice expires while P0 runs, the kernel freezes P0's registers into PCB0, loads P1's registers and page-table pointer (CR3) from PCB1, and transfers control to P1. During the shaded kernel interval, zero user work is performed.

3. Impact of Context Switching on System Performance

  • Direct Overhead: Saving and restoring dozens of general-purpose/floating-point registers and kernel stack pointers takes several microseconds of pure CPU overhead.
  • Indirect (Microarchitectural) Overhead: Switching address spaces flushes or invalidates the TLB (Translation Lookaside Buffer) (unless tagged with ASIDs) and pollutes CPU L1/L2 caches, causing cold-cache misses immediately after the new process resumes.
  • Design Trade-Off: Choosing a tiny Round-Robin time quantum increases context-switch frequency and lowers throughput; choosing a huge quantum degrades interactive response time.

4. Key Takeaways

  • Hardware support such as multiple register sets (Sun UltraSPARC) or hardware context descriptors reduces direct switch latency.
  • Switching between threads of the same process avoids reloading the page table and flushing the TLB, making thread switching far cheaper than process switching.
Q3. Explain Long-Term, Short-Term, and Medium-Term Schedulers with a queueing diagram. Describe CPU Scheduling Criteria and compare Preemptive vs Non-Preemptive scheduling. 7 Marks • SPPU QB U2-Q3/Q4 & SPPU Oct 2025 Q3b
SPPU Marking Split: Queueing Diagram SVG + Explanation (2.5M) · 3-Scheduler Comparison Table (2M) · Scheduling Criteria & Preemption Table (2M) · Takeaways (0.5M)

1. Definition & Core Principle

A Process Scheduler is an OS kernel subsystem that selects the next eligible job or process from waiting queues to receive memory or CPU time. Scheduling occurs across three time horizons: Long-Term (job admission), Medium-Term (swapping), and Short-Term (CPU dispatch).

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam)
  • Long-Term Scheduler: Admits jobs from Disk Job Pool into the RAM Ready Queue, controlling the degree of multiprogramming and balancing I/O-bound vs CPU-bound processes.
  • Short-Term Scheduler: Selects one ready process every few milliseconds; the Dispatcher then performs the context switch and jumps to the user program.
  • Medium-Term Scheduler: Swaps partially executed processes out to disk during heavy memory contention and swaps them back in later.

3. Comparison of Schedulers, Scheduling Criteria & Preemption

FeatureLong-Term SchedulerShort-Term SchedulerMedium-Term Scheduler
AliasJob SchedulerCPU SchedulerSwapper
Invocation SpeedSlowest (seconds or minutes)Fastest (every few milliseconds)Intermediate
TransitionDisk Job Pool → Ready Queue (RAM)Ready Queue → Running (CPU)RAM ↔ Swap Disk
Primary ObjectiveControl degree of multiprogrammingKeep CPU maximally busy and responsiveReduce memory contention / thrashing

Scheduling Criteria: Maximize CPU Utilization (40–90%) and Throughput (processes completed per unit time); minimize Turnaround Time ($TAT = CT - AT$), Waiting Time ($WT = TAT - BT$), and Response Time ($RT = \text{First Run} - AT$).

Preemptive vs Non-Preemptive: Non-preemptive algorithms (FCFS, non-preemptive SJF) allow a process to hold the CPU until completion or I/O wait (low switch overhead, poor interactivity). Preemptive algorithms (SRTF, Round Robin, Preemptive Priority) forcibly interrupt running jobs on higher-priority arrivals or timer expiration (essential for time-sharing and RTOS, requires synchronization on shared kernel structures).

4. Key Takeaways

  • Modern time-sharing OSes like Linux/Windows often omit a standalone Long-Term Scheduler, loading new processes directly into the Ready Queue and relying on Medium-Term swapping/paging if RAM fills.
Q4. Define a Thread. Compare Process vs Thread and User-Level Threads (ULT) vs Kernel-Level Threads (KLT). Explain Many-to-One, One-to-One, and Many-to-Many multithreading models with neat diagrams. 6 Marks • SB Patil U2-Q9/Q12 & Syllabus Unit II
SPPU Marking Split: Thread Definition & Shared/Private Resources (1M) · Multithreading Models SVG + Explanation (2M) · ULT vs KLT & Process vs Thread Tables (2M) · POSIX Code Example (1M)

1. Definition & Core Principle

A Thread (lightweight process) is the smallest independent unit of CPU execution inside a process. Each thread maintains its own Thread ID, Program Counter, register set, and stack, while sharing the process's code section, data section, heap, and open files with peer threads.

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam)
  • Many-to-One: Multiple user threads map to a single kernel thread; fast user-space switching, but no multicore parallelism and any blocking system call freezes the whole process.
  • One-to-One: Each user thread maps 1:1 to a dedicated kernel thread (Linux NPTL, Windows). Enables true multicore execution and non-blocking concurrency, capped only by kernel thread overhead.
  • Many-to-Many: Multiplexes $M$ user threads onto $N$ ($N \le M$) kernel threads, combining lightweight user-thread creation with multicore parallelism.

3. Comparison: User-Level Threads (ULT) vs Kernel-Level Threads (KLT)

CriterionUser-Level Threads (ULT)Kernel-Level Threads (KLT)
Managed ByUser-space library (OS kernel sees only 1 process).OS Kernel directly via kernel thread table.
Creation & Switching SpeedVery fast (no trap or mode switch required).Slower (requires system call and kernel mode switch).
Blocking System CallBlocks all peer threads in the same process.Kernel schedules another thread from the same process.
Multicore ParallelismNot possible (entire process scheduled on 1 core).True parallel execution across multiple CPU cores.
OS PortabilityRuns on any OS without kernel modification.Requires kernel-specific APIs (e.g., POSIX clone()).
 
// POSIX Kernel-Level Thread Creation (compile with: gcc prog.c -lpthread)
#include <stdio.h>
#include <pthread.h>

void *task(void *arg) {
    printf("Worker Thread #%d running\n", *(int *)arg);
    return NULL;
}
int main(void) {
    pthread_t tid; int id = 1;
    pthread_create(&tid, NULL, task, &id);
    pthread_join(tid, NULL);
    return 0;
}

4. Key Takeaways

Q1. Explain Race Condition and the Critical Section Problem. State the three mandatory requirements for a valid solution and explain Peterson's two-process software solution with C pseudocode and correctness verification. 6 Marks • SPPU QB U3-Q1/Q3 & SB Patil U3-Q3/Q5
SPPU Marking Split: Race Condition & CS Anatomy (1.5M) · Three Mandatory Requirements (1.5M) · Peterson's C Code (2M) · Proof of Requirements (1M)

1. Definition & Core Principle

A Critical Section (CS) is a code segment in which a cooperating process accesses shared data structures (variables, files, buffers) that must not be executed concurrently by multiple processes. A Race Condition occurs when multiple processes read and write shared data simultaneously such that the final result depends unpredictably on the exact instruction-interleaving order.

2. Anatomy of Critical Section & Three Mandatory Requirements

Every cooperating process follows four sections: Entry Section (requests permission to enter) → Critical Section (modifies shared data) → Exit Section (releases permission) → Remainder Section (non-shared code). A valid software/hardware solution must satisfy all three conditions:

  1. Mutual Exclusion: If process $P_i$ is executing inside its critical section, no other process $P_j$ ($j \neq i$) can execute inside its critical section simultaneously.
  2. Progress: If no process is inside its critical section and some processes wish to enter, only processes not in their remainder section may participate in deciding who enters next, and this selection cannot be postponed indefinitely.
  3. Bounded Waiting: There exists an upper bound on the number of times other processes are allowed to enter their critical sections after a process has requested entry and before that request is granted (prevents starvation).

3. Peterson's Solution (Two-Process Software Synchronization)

Peterson's algorithm coordinates two processes $P_0$ and $P_1$ using two shared variables: bool flag[2] (intent to enter CS) and int turn (yields turn politely to the other process).

// Peterson's Algorithm for Process i (where j = 1 - i)
#include <stdbool.h>

bool flag[2] = {false, false};
int turn = 0;

void process(int i) {
    int j = 1 - i;
    while (true) {
        flag[i] = true;                 // 1. Express desire to enter CS
        turn = j;                       // 2. Give priority to the other process
        while (flag[j] && turn == j) {
            ;                           // 3. Busy-wait only if Pj wants in & it's Pj's turn
        }
        /* ===== CRITICAL SECTION ===== */
        flag[i] = false;                // 4. Exit section: release CS
        /* ===== REMAINDER SECTION ===== */
    }
}

4. Correctness Verification & Key Takeaways

  • Mutual Exclusion Holds: Both $P_0$ and $P_1$ could be in CS simultaneously only if flag[0] == flag[1] == true and both exited their while loops; impossible because turn holds only one value ($0$ or $1$) at a time.
  • Progress & Bounded Waiting Hold: If $P_j$ is not interested (flag[j] == false), $P_i$ enters immediately. If both contend, whichever writes turn last lets the other enter first; upon exit, $P_j$ sets flag[j] = false (or resets turn = i if re-entering), guaranteeing $P_i$ waits at most one turn.
  • Limitation: On modern out-of-order CPUs, instruction reordering requires memory-fence/barrier instructions around flag and turn; it also uses busy-waiting (spinlock).
Q2. What is a Semaphore? Explain Binary and Counting Semaphores with atomic wait() and signal() blocking implementations. Compare Mutex, Semaphore, and Monitor with a Monitor example. 7 Marks • SPPU QB U3-Q2/Q8 & SPPU Oct 2025 Q6a
SPPU Marking Split: Semaphore Definition & Types (1.5M) · Atomic Blocking Code (2M) · Mutex vs Semaphore vs Monitor Table (2M) · Monitor Example (1.5M)

1. Definition & Core Principle

A Semaphore $S$ (introduced by Dijkstra) is an integer synchronization variable accessed strictly through two indivisible (atomic) operations: wait(S) (or P(S), decrements $S$) and signal(S) (or V(S), increments $S$). A Binary Semaphore ranges over $\{0, 1\}$ (used for mutual exclusion/signaling), whereas a Counting Semaphore ranges over an unrestricted integer domain (tracks $N$ available instances of a resource).

2. Atomic Blocking Semaphore Implementation (Avoiding Busy-Waiting)

To eliminate CPU waste from spinlocks, a blocking semaphore associates an internal waiting queue (list) with the integer value. When $S < 0$, the calling process blocks itself (moves to Waiting state) and yields the CPU:

typedef struct {
    int value;
    struct process_queue *list;
} semaphore;

void wait(semaphore *S) {               // P(S) - executed atomically
    S->value--;
    if (S->value < 0) {
        add_this_process_to(S->list);
        block();                        // Suspend process (no busy wait)
    }
}

void signal(semaphore *S) {             // V(S) - executed atomically
    S->value++;
    if (S->value <= 0) {
        PCB *P = remove_process_from(S->list);
        wakeup(P);                      // Move P from Waiting to Ready queue
    }
}

Key property: When S->value is negative, $|S\text{->value}|$ equals the exact number of processes currently blocked waiting on semaphore $S$.

3. Deadlock-Free Solutions

// 1. Bounded-Buffer Producer-Consumer (mutex=1, empty=N, full=0)
void producer(void) {
    while (true) {
        item next = produce();
        wait(empty);        // Must come BEFORE wait(mutex) to avoid deadlock!
        wait(mutex);
        insert_item(next);
        signal(mutex);
        signal(full);
    }
}
void consumer(void) {
    while (true) {
        wait(full);         // Must come BEFORE wait(mutex)
        wait(mutex);
        item x = remove_item();
        signal(mutex);
        signal(empty);
        consume(x);
    }
}

// 2. Dining Philosophers Asymmetric Deadlock-Free Solution (chopstick[5] = {1,1,1,1,1})
void philosopher(int i) {
    while (true) {
        think();
        if (i % 2 == 0) {                   // Even grabs RIGHT first, then LEFT
            wait(chopstick[(i + 1) % 5]);
            wait(chopstick[i]);
        } else {                            // Odd grabs LEFT first, then RIGHT
            wait(chopstick[i]);
            wait(chopstick[(i + 1) % 5]);
        }
        eat();
        signal(chopstick[i]);
        signal(chopstick[(i + 1) % 5]);
    }
}

4. Key Takeaways

  • Critical Order Rule: In Producer-Consumer, swapping wait(empty) and wait(mutex) causes deadlock when the buffer is full (Producer holds mutex waiting for Consumer, who blocks on mutex).
  • Alternative Dining Philosophers fixes: (a) allow at most 4 philosophers at the table (semaphore room = 4), or (b) use a Monitor to pick up both chopsticks atomically.

Q5. Define Deadlock and differentiate it from Starvation. State Coffman's four necessary conditions, explain Resource Allocation Graph (RAG) cycle detection with diagrams, and summarize Deadlock Prevention, Avoidance, Detection, and Recovery. 7 Marks • SPPU QB U3-Q5/Q7 & SPPU Oct 2025 Q5b
SPPU Marking Split: Definition & Coffman's 4 Conditions (2M) · RAG Single vs Multi-Instance SVG + Explanation (2.5M) · Handling Methods & Recovery (2M) · Deadlock vs Starvation (0.5M)

1. Definition & Coffman's Four Necessary Conditions

A Deadlock is a permanent blocking situation where a set of two or more processes wait indefinitely because every process in the set holds a resource needed by another process in the same set. Deadlock can occur if and only if all four of Coffman's conditions hold simultaneously:

  1. Mutual Exclusion: At least one resource must be non-sharable (held by only one process at a time).
  2. Hold and Wait: A process holds at least one allocated resource while waiting to acquire additional resources currently held by others.
  3. No Preemption: Resources cannot be forcibly reclaimed by the OS; they are released only voluntarily after the holding process finishes.
  4. Circular Wait: A closed chain $\{P_1, P_2, \dots, P_n\}$ exists where $P_1$ waits for a resource held by $P_2$, ..., and $P_n$ waits for a resource held by $P_1$.

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam)
  • Vertices & Edges: Circles denote Processes ($P_i$), rectangles denote Resource Types ($R_j$) containing dots for instances. A Request Edge ($P_i \to R_j$) indicates $P_i$ is waiting for $R_j$; an Assignment Edge ($R_j \to P_i$) indicates an instance is held by $P_i$.
  • RAG Theorem: No cycle = Guaranteed no deadlock. If a cycle exists and every resource has 1 instance, deadlock is guaranteed. If resources have multiple instances, a cycle is a necessary but not sufficient condition (e.g., $P_2, P_4$ can finish and break the cycle).

3. Deadlock Handling Strategies & Deadlock vs Starvation

  • Deadlock Prevention: Statically falsifies at least one Coffman condition: (a) spool/share resources (breaks Mutual Exclusion), (b) require all resources upfront (breaks Hold & Wait), (c) preempt resources when a new request fails (breaks No Preemption), or (d) impose strict numerical ordering $R_1 < R_2 < \dots$ (breaks Circular Wait).
  • Deadlock Avoidance: Dynamically checks safe states before granting requests (Banker's Algorithm).
  • Deadlock Detection & Recovery: Uses Wait-For Graph (single instance) or detection matrix periodically, then recovers via Process Termination (abort all or abort one-by-one) or Resource Preemption (select victim, rollback state, guard against starvation).

Deadlock vs Starvation: Deadlock is a permanent cycle where involved processes are blocked waiting on each other forever. Starvation occurs when a process is repeatedly bypassed by higher-priority jobs even though resources eventually become free (solved by Aging).

1. Definition & Logical vs Physical Address

Paging is a non-contiguous memory management technique that divides physical RAM into fixed-size Frames and a process's logical memory into equal-sized Pages, eliminating external fragmentation. The MMU (Memory Management Unit) translates every CPU-generated Logical Address $(p, d)$ into a Physical Address $(f, d)$ at runtime, accelerated by an associative hardware cache called the TLB (Translation Lookaside Buffer).

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam)
  • Address Split: CPU splits a logical address into Page Number $p$ and Offset $d$ (e.g., for 32-bit address and 4 KB page $= 2^{12}$ bytes, lower 12 bits = $d$, upper 20 bits = $p$).
  • TLB Hit Path ($\alpha$): Associative parallel search finds $p \to f$ inside TLB in $t_{\text{TLB}}$ time, then reads target data from RAM in $t_{\text{mem}}$ (only 1 RAM cycle).
  • TLB Miss Path ($1 - \alpha$): Hardware reads Page Table in RAM (1st RAM access) to retrieve $f$, updates the TLB, and fetches actual data at $(f, d)$ (2nd RAM access).

3. Page Table Structures & EMAT Worked Numerical

Large Page Table Solutions: (1) Hierarchical (Multi-level) Paging pages the page table itself, (2) Hashed Page Tables map sparse 64-bit virtual pages via hash buckets, and (3) Inverted Page Table maintains strictly 1 entry per physical RAM frame (indexed by $\langle \text{pid}, p \rangle$), drastically shrinking memory overhead.

Effective Memory Access Time (EMAT) Derivation & Solved Numerical

$$\text{EMAT} = \alpha \cdot (t_{\text{TLB}} + t_{\text{mem}}) + (1 - \alpha) \cdot (t_{\text{TLB}} + 2 \cdot t_{\text{mem}})$$

Given: Hit Ratio $\alpha = 80\% = 0.80$, $t_{\text{TLB}} = 20\text{ ns}$, $t_{\text{mem}} = 100\text{ ns}$:
$\text{EMAT} = 0.80 \times (20 + 100) + (1 - 0.80) \times (20 + 2 \times 100) = 0.80(120) + 0.20(220) = 96 + 44 = \mathbf{140\text{ ns}}$.

1. Definitions & Core Principle

Virtual Memory separates a user process's logical memory from physical RAM, enabling programs larger than available RAM to run and increasing the degree of multiprogramming. Demand Paging implements virtual memory by loading pages into physical frames lazily (only when accessed during execution); non-resident pages remain on backing store (swap disk) marked invalid (i) in the Page Table.

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam — All 6 Steps)
  • Step 1: Process accesses a memory reference whose Page Table Entry has valid-invalid bit set to i (invalid).
  • Step 2: Hardware triggers a Page Fault Trap to the OS kernel.
  • Step 3: OS checks an internal PCB table: if the reference is illegal, terminate process; otherwise locate the page on the Backing Store (disk).
  • Step 4: OS finds a free physical frame (or evicts a victim page via replacement algorithm) and schedules a disk read into the frame.
  • Step 5: Once disk I/O finishes, OS updates the Page Table entry with frame number and changes the bit to v (valid).
  • Step 6: OS restarts the exact instruction interrupted by the trap; the page is now resident and executes normally.

3. Benefits & Effective Access Time Formula

Demand Paging Effective Access Time

$$\text{EAT} = (1 - p) \cdot ma + p \cdot \text{Page Fault Service Time}$$

where $p \in [0, 1]$ is the probability of a page fault and $ma$ is normal RAM access time (~100 ns). Because disk service takes ~8 ms ($8{,}000{,}000\text{ ns}$), keeping $p < 0.00001$ is critical to avoid performance collapse.

  • Benefits of Virtual Memory: Allows programs larger than physical RAM, improves CPU utilization via higher multiprogramming, enables Copy-on-Write fast fork(), and simplifies shared libraries.

Q6. Explain Thrashing, its root causes, and how the Working Set Model (Denning) and Page-Fault Frequency (PFF) mechanisms detect and prevent Thrashing. 5 Marks • SPPU QB U4-Q8 & SB Patil U4-Q20b
SPPU Marking Split: Definition & Cause of Thrashing (1.5M) · Thrashing & Working Set SVG + Explanation (2M) · Working Set & PFF Solutions (1.5M)

1. Definition & Cause of Thrashing

Thrashing is a state of severe system performance collapse in which processes spend more time swapping pages between RAM and disk (paging I/O) than executing instructions. It arises when the sum of active pages needed by all running processes exceeds available physical frames ($D > m$), causing continuous page faults and plummeting CPU utilization.

2. Neat Labelled Diagram & Diagram Explanation

Diagram Explanation (How to Describe in Exam)
  • Thrashing Trap (Left): Initially, adding more jobs boosts CPU utilization. Beyond the optimal knee, RAM is overcommitted, fault rates explode, and the OS misinterprets low CPU activity as under-loading — admitting even more jobs and crashing throughput.
  • Working Set Window (Right): Tracks the distinct pages referenced within the most recent $\Delta$ references. If total working-set demand $D = \sum WSS_i > m$, the OS suspends one or more processes so remaining jobs keep their full working sets in RAM.

3. Thrashing Prevention Techniques

  • Working Set Model: Ensures each active process receives at least $WSS_i$ frames based on the Principle of Locality.
  • Page-Fault Frequency (PFF): Sets upper and lower fault-rate bounds per process. If fault rate exceeds the upper bound, allocate an extra frame; if below the lower bound, reclaim a frame; if no free frames remain while a process hits the upper bound, swap out a process.
  • Local Replacement Policy: Prevents a thrashing process from stealing frames belonging to healthy neighbor processes (unlike Global Replacement).
